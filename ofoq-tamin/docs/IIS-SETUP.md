# راهنمای کامل اجرای پروژه روی هاست ویندوز (IIS / Plesk / WebHostPanel)

این سند مخصوص حالتی است که سایت روی هاست ویندوز بالا نمی‌آید (خطای ۵۰۰، صفحه سفید، دانلود شدن فایل PHP و…).
اگر روی هاست لینوکس هستید، بخش ۹-ب فایل `README.md` کافی است.

> خلاصه یک‌خطی: روی IIS، «بالا نیامدن PHP» تقریباً همیشه یکی از این چهار علت را دارد:
> **۱) هندلر PHP برای دامنه ثبت نشده، ۲) یک بخش قفل‌شده در `web.config`،
> ۳) نبود افزونه `pdo_sqlite`/`mbstring`، ۴) دسترسی نوشتن پوشه و مسیر نشست‌ها.**

---

## ۱. چک‌لیست سریع (به همین ترتیب انجام دهید)

| # | کار | نتیجه مورد انتظار |
|---|---|---|
| ۱ | بسته ZIP را کامل استخراج کنید. باید `index.php`، `config.php`، `web.config`، پوشه‌های `inc`، `views`، `tmp` را کنار هم داشته باشید | ساختار پوشه‌ها حفظ شود |
| ۲ | همه فایل‌ها را با FTP در حالت **Binary** آپلود کنید (نه ASCII) | فایل‌ها بایت‌به‌بایت سالم |
| ۳ | در پنل هاست، نسخه PHP را روی **۸.۰ یا بالاتر** بگذارید (حداقل ۷.۴) | `PHP_SAPI = cgi-fcgi` |
| ۴ | افزونه‌های `pdo_sqlite` و `mbstring` را فعال کنید | `check.php` سبز شود |
| ۵ | به پوشه سایت دسترسی **Modify** برای `IIS_IUSRS` بدهید | ساخت `parssaze.db` و `tmp/sessions` |
| ۶ | `https://دامنه/check.php` را باز کنید | همه ردیف‌ها سبز |
| ۷ | `https://دامنه/index.php` را باز کنید | صفحه اصلی فروشگاه |

## ۲. تشخیص نوع خطا از روی شماره آن

روی IIS شماره خطا معنای دقیقی دارد؛ اول این را از مرورگر یا از
`http://دامنه/` بخوانید:

### الف) خطای ۵۰۰.۱۹ — «This configuration section cannot be used at this path»

یعنی IIS نتوانسته `web.config` را بخواند؛ یا ساختار XML آن خراب است، یا یکی از بخش‌های آن
توسط مدیر سرور **قفل (locked)** شده است.

**راه‌حل گام‌به‌گام:**
1. نام فایل را موقتاً به `web.config.off` تغییر دهید و دوباره صفحه را باز کنید.
   - اگر سایت باز شد → مقصر همین فایل است، برو مرحله ۲.
   - اگر باز نشد → مشکل جای دیگری است (بخش ۲-ب یا ۲-پ را ببینید).
2. فایل `web.config` بسته ما **حداقلی** است: فقط `defaultDocument` و `directoryBrowse`.
   این دو بخش روی همه هاست‌های اشتراکی آزاد هستند. اگر باز هم ۵۰۰.۱۹ گرفتید، یعنی فایل
   در انتقال FTP **خراب شده** است (بند ۶ همین سند) یا هاست شما حتی این دو بخش را هم قفل کرده؛
   در آن حالت با `web.config.off` کار کنید، زیرا این برنامه **به هیچ rewrite و تنظیم IIS دیگری نیاز ندارد**
   (مسیریابی با `index.php?page=...` انجام می‌شود).
3. اگر بخش‌های **اختیاری** داخل کامنت را از حالت توضیح خارج کرده‌اید، یکی‌یکی این کار را کنید و
   بعد از هر تغییر صفحه را رفرش کنید. بخش‌های `handlers`، `modules`، `rewrite`، `authentication`
   و `fastCgi` روی بیشتر هاست‌های اشتراکی قفل‌اند و **نباید** فعال شوند.
   صفحه `check.php` همین موضوع را در ردیف «بخش‌های فعال در فایل» گزارش می‌کند.

### ب) خطای ۵۰۰.۰ / ۵۰۰.۱ / «FastCGI process exited unexpectedly»

یعنی PHP اصلاً اجرا نشد.

- در پنل، نسخه PHP برای دامنه انتخاب نشده است.
  **Plesk:** `Websites & Domains` ← نام دامنه ← `PHP Settings` ← انتخاب نسخه (مثلاً 8.2) ← `OK`.
- مسیر `php-cgi.exe` در تنظیمات سرور اشتباه است → از پشتیبانی هاست بخواهید اصلاح کند.
- افزونه‌ای که PHP در `php.ini` فراخوانی کرده ولی روی سرور نیست، باعث خروج فوری فرایند می‌شود
  (پشتیبانی هاست باید `php.ini` را اصلاح کند).
- فایل `.user.ini` خراب (مثلاً با کدگذاری اشتباه) → آن را موقتاً حذف/تغییرنام دهید.

### پ) خطای ۵۰۰ عمومی (بدون جزئیات) یا صفحه سفید

یعنی PHP اجرا شد ولی برنامه خطا داد.

1. `check.php` را باز کنید؛ ردیف‌های قرمز معمولاً علت را نشان می‌دهند.
2. اگر هنوز صفحه سفید است، در پنل هاست «نمایش خطاهای PHP» (`display_errors`) را روشن کنید.
   در این بسته مقدار آن در `.user.ini` روی `On` است؛ توجه کنید PHP این فایل را تا
   `user_ini.cache_ttl` ثانیه (پیش‌فرض ۳۰۰ = ۵ دقیقه) کش می‌کند، پس بعد از هر تغییر چند دقیقه
   صبر کنید یا در Plesk گزینه `Restart Application` / `Recycle Application Pool` را بزنید.
3. متن واقعی خطا را از این‌جاها بخوانید:
   - **Event Viewer ویندوز:** `Windows Logs` ← `Application` (منبع: `FastCGI` یا `W3SVC`)
   - **فایل لاگ PHP:** مسیر آن در ردیف `log_errors / error_log` صفحه `check.php` نوشته شده است.
   - **لاگ IIS:** پوشه `%SystemDrive%\inetpub\logs\LogFiles\W3SVC…`
4. این نسخه از برنامه خودش هم صفحه خطای فارسی نشان می‌دهد (به‌جای صفحه سفید) و نام فایل و
   شماره خط را چاپ می‌کند.

### ت) مرورگر فایل PHP را دانلود می‌کند یا متن کد را نشان می‌دهد

یعنی هندلر PHP روی این دامنه ثبت نشده است.

- **Plesk:** `Websites & Domains` ← `PHP Settings` ← انتخاب نسخه PHP.
- **پنل‌های دیگر:** بخش `Handler Mappings` / `PHP` / `Select PHP Version`.
- ⚠️ **هرگز** هندلر PHP را دستی داخل `web.config` تعریف نکنید؛ با تنظیمات سراسری هاست
  تعارض می‌کند و خطای ۵۰۰.۱۹/۵۰۰.۰ می‌دهد.

### ث) خطای ۴۰۳.۱۴ یا نمایش فهرست فایل‌های پوشه

سند پیش‌فرض `index.php` ثبت نشده است.

- فایل `web.config` را کنار `index.php` بگذارید (بخش `defaultDocument` همین کار را می‌کند)،
- یا آدرس را به شکل `https://دامنه/index.php` باز کنید.

### ج) خطای ۴۰۴.۳ برای فایل‌های CSS/فونت

روی IIS قدیمی (۷.۵) نوع فایل `.woff2` تعریف نشده است. این سایت فونت را از CDN می‌خواند،
ولی اگر فونت را محلی کنید، بخش (۶) داخل `web.config` را از حالت توضیح خارج کنید.

## ۳. دسترسی نوشتن (مهم‌ترین علت خطای «پایگاه داده» و «ورود نمی‌ماند»)

برنامه دو چیز روی دیسک می‌نویسد: فایل `parssaze.db` (پایگاه داده) و پوشه `tmp/sessions`
(فایل‌های نشست). هر دو باید برای کاربر اجرای PHP قابل نوشتن باشند.

### روش گرافیکی (RDP / File Manager پنل)
1. روی پوشه سایت راست‌کلیک ← `Properties` ← تب `Security` ← `Edit`
2. `Add` ← نام `IIS_IUSRS` را وارد کنید (و در Plesk معمولاً `<نام‌کاربری_پنل>` هم لازم است)
3. تیک `Modify` را بزنید ← `OK`

### روش خط فرمان (اگر دسترسی RDP یا Command Prompt دارید)

```cmd
:: به‌جای C:\inetpub\vhosts\example.com\httpdocs مسیر واقعی سایت خود را بگذارید
icacls "C:\inetpub\vhosts\example.com\httpdocs" /grant "IIS_IUSRS:(OI)(CI)M" /T

:: نام Application Pool (اگر به‌جای IIS_IUSRS می‌خواهید):
icacls "C:\path\to\site" /grant "IIS AppPool\DefaultAppPool:(OI)(CI)M" /T

:: بررسی وضعیت مجوزها
icacls "C:\path\to\site"
```

### اگر پوشه را قابل نوشتن نکردید
- برنامه باز هم بالا می‌آید ولی در ساختن `parssaze.db` و نگه‌داشتن نشست‌ها مشکل پیدا می‌کند.
- در این حالت پیام «خطا در اتصال به پایگاه داده» یا «ورود انجام می‌شود ولی نمی‌ماند» می‌بینید.
- `check.php` دقیقاً می‌گوید کدام مسیر قابل نوشتن نیست (ردیف‌های «نوشتن واقعی در پوشه پروژه» و
  «پوشه tmp/sessions»).

## ۴. نشست‌ها (Session) و مشکل «ورود انجام می‌شود ولی وارد پنل نمی‌شود»

روی IIS معمولاً `fastcgi.impersonate = 1` است؛ یعنی PHP با هویت کاربر درخواست‌کننده اجرا می‌شود
و به پوشه موقت ویندوز دسترسی نوشتن ندارد. نتیجه: `session_start()` خطا می‌دهد و ورود کاربر
ثبت نمی‌شود.

**راه‌حل اعمال‌شده در این نسخه:** فایل `config.php` قبل از `session_start()` این کارها را انجام می‌دهد:

1. مقدار `session.save_path` سرور را بررسی می‌کند.
2. اگر مسیر پیش‌فرض خالی یا غیرقابل نوشتن بود، پوشه `tmp/sessions` را می‌سازد و از آن استفاده می‌کند.
3. اگر هیچ‌کدام ممکن نبود، برنامه با پیام راهنما ادامه می‌دهد و در `check.php` هشدار می‌دهد.
4. برای جلوگیری از انباشت فایل‌های نشست (ویندوز Task Scheduler ندارد)، با احتمال کم
   فایل‌های منقضی را پاک می‌کند.

> اگر می‌خواهید مسیر نشست را دستی تعیین کنید، در `.user.ini` خط زیر را از حالت توضیح خارج کنید:
> ```ini
> session.save_path = "C:\inetpub\vhosts\example.com\tmp\sessions"
> ```
> توجه: مسیر باید برای کاربر PHP قابل نوشتن باشد و PHP این فایل را تا ۵ دقیقه کش می‌کند.

## ۵. کدگذاری و انتقال فایل (علت خرابی متن فارسی و خرابی `web.config`)

- همیشه با حالت انتقال **Binary** آپلود کنید. انتقال ASCII، بایت‌های UTF-8 را خراب می‌کند.
  اگر متن فارسی سایت به‌شکل «؟؟؟» یا کاراکترهای عجیب دیده می‌شود، همین اتفاق افتاده است.
- علائم خرابی `web.config` با انتقال ASCII: کاراکترهای نامعتبر در توضیح‌ها ← XML نامعتبر ←
  خطای ۵۰۰.۱۹ برای همه صفحات. برای همین، فایل‌های `web.config`، `.user.ini` و `.htaccess`
  این بسته **فقط با کاراکترهای انگلیسی** نوشته شده‌اند تا این ریسک صفر شود.
- `check.php` هم سلامت XML، وجود BOM و وجود کاراکترهای غیرانگلیسی در `web.config` را بررسی می‌کند.
- اگر شک دارید فایل خراب شده، همان فایل را از بسته ZIP اصلی دوباره آپلود کنید.

## ۶. معادل فایل‌های لینوکس در IIS

| فایل لینوکس | معادل ویندوز | وضعیت در این بسته |
|---|---|---|
| `.htaccess` | `web.config` | هر دو در بسته هستند؛ هر سرور فایل مربوط به خودش را می‌خواند |
| `DirectoryIndex` | `<defaultDocument>` | فعال در `web.config` |
| `IndexIgnore` / `Options -Indexes` | `<directoryBrowse enabled="false">` | فعال در `web.config` |
| `Require all denied` | `<requestFiltering>` | بخش اختیاری کامنت‌شده |
| `Header set …` | `<httpProtocol><customHeaders>` | بخش اختیاری کامنت‌شده |
| `php_flag/php_value` | `.user.ini` (روی PHP 8 خوانده می‌شود) یا پنل هاست | `.user.ini` در بسته هست |

## ۷. دستورات مفید برای مدیر سرور (اختیاری)

```cmd
:: نمایش نسخه PHP ثبت‌شده برای سایت
%windir%\system32\inetsrv\appcmd list config "Default Web Site" -section:system.webServer/handlers

:: ری‌استارت Application Pool (برای اعمال فوری .user.ini)
%windir%\system32\inetsrv\appcmd recycle apppool "DefaultAppPool"

:: آزمون اجرای php-cgi روی سرور
"C:\Program Files\PHP\v8.2\php-cgi.exe" -v

:: اجرای برنامه با سرور داخلی PHP (برای بررسی سالم بودن کد)
php -S localhost:8000
```

## ۸. عیب‌یاب خودکار `check.php`

با باز کردن `https://دامنه/check.php` این موارد بررسی و به‌صورت جدول فارسی نمایش داده می‌شوند:

- نسخه PHP، حالت اجرا (`PHP_SAPI`)، فایل `php.ini` فعال، محدودیت حافظه و زمان اجرا
- افزونه‌های ضروری و اختیاری + فهرست درایورهای `PDO`
- کامل بودن فایل‌های پروژه
- **آزمون واقعی نوشتن روی دیسک** در پوشه پروژه، `tmp` و `tmp/sessions`
  (روی ویندوز `is_writable()` تنها قابل اعتماد نیست)
- **آزمون عملی ساخت، نوشتن و خواندن نشست**
- **آزمون کامل SQLite**: اتصال، `INSERT`، `SELECT`، `DROP` و `PRAGMA integrity_check`
- اطلاعات سرور: نرم‌افزار، پورت، `APPL_PHYSICAL_PATH`، `APP_POOL_ID`
- تنظیمات مهم PHP: `open_basedir`، `disable_functions`، `error_log`، `default_charset` و…
- موارد مخصوص IIS: `fastcgi.impersonate`، `cgi.fix_pathinfo`، `fastcgi.logging`،
  مسیر `php-cgi.exe`، متغیر `PHP_FCGI_MAX_REQUESTS`
- **اثرگذاری `.user.ini`**: کدام تنظیمات واقعاً اعمال شده و کدام نشده
- **بازرسی `web.config`**: اعتبار XML، وجود BOM، کاراکترهای غیرانگلیسی،
  فهرست بخش‌های فعال و تشخیص بخش‌های پرخطر/قفل‌شده
- بازرسی `.htaccess` برای دستورهای پرخطر خارج از `IfModule`
- نمایش انتهای فایل `error_log` (در صورت قابل خواندن بودن)

> ⚠️ **پس از رفع مشکل، فایل `check.php` را از هاست حذف کنید**؛ این فایل اطلاعات سرور را نشان می‌دهد.
